Why AI Agents Need Guardrails

An LLM is a powerful generalist — but without structure, it improvises everything.

📏 Rules

Without explicit coding standards, agents produce code that works but doesn't match your stack conventions, naming patterns, or security requirements. Every prompt starts from zero.

🎭 Personas

An agent can be an architect, an implementer, or a reviewer — but only if you tell it which hat to wear. Without personas, it blurs roles and skips approval gates.

🛠️ Skills

Repeatable workflows (spec → plan → implement → review) need to be captured as reusable commands, not re-described each time. Skills turn tribal knowledge into executable process.

📁 Templates

Specs, plans, ADRs, and briefs need consistent structure so agents know what to produce and humans know where to find it. Templates enforce that contract.

Together, these turn an AI agent from a "do whatever" chatbot into a disciplined team member that follows your process.

The Workflow: The Review Loop

The scaffold is built around an iterative lifecycle bound by a Review Loop to ensure alignment at every stage.

           ( IDEA )
              │
              ▼  /create-spec       ── product-analyst drafts brief
          [ BRIEF ]  ◄───────────────┐
              │                      │
              ▼ (⏸ user approval)    │
          [ SPEC ]   ◄───────────────┤ /review
              │                      │ (The Review Loop)
              ▼  /create-plan        │ ── architect drafts spec + ADRs
          [ PLAN ]   ◄───────────────┘
              │
              ├─────────────────────→ [ TEST PLAN ] ── /design-tests
              ▼  /implement
    [ WORKING CODE ] ◄───────────┐  ── /resume-plan reloads context
              │                      │
              │                      │ /review
              ▼  /archive-plan       │ (The Review Loop)
          ( ARCHIVE )   ◄────────────┘
              │
              ▼  /prepare-release    ── release-engineer bumps version
         { RELEASE }

  Cross-cutting:
    refresh-docs      — invoked inline by most skills, regenerates dashboard
    security-review   — standalone deep security review (any time)
    audit-docs        — sweep tree for staleness, drift, or orphans
    investigate       — architectural research → spec/ADR
    manage-deps       — analyze and upgrade dependencies
    integrity-check   — diagnostic: "is my .ai/ install healthy?"

Skills in Detail: From Idea to Plan

/create-spec

product-analyst architect ⏸ approval gate brief + spec + ADRs

The primary entry point for new features. Handles the transition from Idea to Brief (human gate) and Brief to Spec. Guarantees that product intent is captured before technical design begins.

  1. Draft brief as product-analyst → docs/briefs/active/
  2. ⏸ Pause for user approval
  3. Draft spec + ADRs as architect → docs/specs/active/
  4. Refresh docs dashboard

/investigate

architect spec / ADR

Conducts deep technical research or architectural evaluation of a new library, pattern, or refactor. Produces a Spec or ADR with findings and recommendations, skipping the Brief phase.

/create-plan

architect implementer phased plan

Takes an approved spec and breaks it into phased work. Each phase ends in a testable, deployable state. Uses templates/plan.md with progress counters and rule-compliance checklists.

/design-tests

tester test plan

Produces a test plan (behaviours, unit/component/e2e coverage, failure modes) from the spec. Runs in parallel with plan creation to ensure implementation is test-driven.

Skills in Detail: Build, Review, Ship

/implement

implementer code + updated plan

Executes the plan phase by phase, task by task. Ticks checkboxes, moves the 🔄 cursor, and runs tests after every task. Supports pause/resume discipline.

/resume-plan

implementer context → implement

Picks up a paused plan: finds the 🔄 marker, reads the latest Notes entry, reloads the spec and brief for context, then hands off to /implement.

/review

reviewer security-reviewer consolidated review

Unified entry point for all review types. Analyzes context and delegates to review-doc, review-change, and runs a parallel security-review. Consolidates all findings into a single structured response.

/archive-plan

mechanical files → archive/

When a plan reaches status: done, atomically moves the plan and all related artifacts (spec, brief, test-plan) from active/ to archive/.

/prepare-release

release-engineer ⏸ human approval version + notes + tag

Drives the repo from green main to release-ready: version bump, release notes, and annotated tag. Stops before CI trigger or store submission.

Maintenance, Audit & Quality

🔄 /refresh-docs

mechanical

Regenerates the documentation dashboard at docs/README.md. Writes status tables for all active and archived artifacts. Invoked inline by most skills.

🔒 /security-review

security-reviewer

Deep standalone security review. Authors a threat model, maps asset lifecycles, and classifies findings (Block / Change-required / Advisory).

🩺 /integrity-check

mechanical

Diagnostic tool: "is my .ai/ install healthy?" Checks file presence, symlink resolution, and scaffold version. Read-only.

📋 /audit-docs

auditor

Sweeps the docs tree for staleness, missing pieces, or contradictions. Produces a Markdown report highlighting orphaned files or broken links.

🏗️ /audit-structure

auditorarchitect

Validates code organization, folder layout, and module boundaries against stack rules. Identifies drift from established patterns.

📦 /manage-deps

dependency-manager

Analyzes dependencies, resolves vulnerabilities (CVEs), and proposes safe upgrades. Requires approval before installation.

Document Lifecycle

Every artifact (brief, spec, plan) has a status field in frontmatter. Skills enforce transitions — they refuse to consume artifacts in the wrong state.

  Brief:      draft ──→ approved (human gate)

  Spec:       draft ──→ in-review ──→ approved

  Plan:       draft ──→ in-progress ──→ done ──→ archived
                         │            │
                         │  ⏸ pause   │
                         ▼            │
                    (resume-plan) ────┘

  Test Plan:  draft (standalone, archived with parent plan)

  ADRs:       accepted │ superseded │ deprecated
               (never moved — always in decisions/)

Key Invariants

  • Cross-linking: Brief ID → Spec → Plan → Test Plan. Every artifact knows its relatives via related.* frontmatter.
  • Dashboard sync: /refresh-docs is triggered after every doc mutation — the dashboard is always current.
  • Archive atomicity: /archive-plan moves all related files together or fails loudly.
  • ADRs are permanent: Never archived, never deleted. They accumulate as project history.

The Fragmentation Problem

OK, so agents need rules, personas, and skills. But now multiply by tools and repos.

Agent silos

Claude Code, Gemini CLI, and Copilot CLI each expect different config files in different directories. Skills that work in one tool don't exist in another.

Claude  → CLAUDE.md, .claude/skills/
Gemini  → GEMINI.md, .gemini/commands/
Copilot → .github/copilot-instructions.md

Three tools × three formats = constant busywork keeping them aligned.

Repo silos

When you copy-paste rules and skills into each project, they inevitably drift. Good prompt engineering stays trapped in one repo.

repo-A/  → rules v1.2, 8 skills
repo-B/  → rules v1.0, 6 skills  ← stale
repo-C/  → rules v1.3, 9 skills  ← custom fork
           ↑ no single source of truth

Updates require N × manual merges.

The Answer: One Submodule, Zero Drift

A git submodule gives you a single source of truth that every repo and every agent tool shares.

✓ Shared Workflow

Skills, rules, personas, and templates live in one place. git submodule update --remote brings every repo up to date in seconds.

✓ No Rules Drift

Coding standards, security rules, and stack conventions are versioned. Changes propagate to all repos — no copy-paste, no merge conflicts.

✓ Agent-Agnostic

Symlinks map one set of skills/rules to every tool's expected paths. Write once, use from Claude, Gemini, and Copilot identically.

✓ Fork & Adapt

Fork the submodule for your company. Override per-project in .ai/. The scaffolding is opinionated but never locked-in.

Architecture: What's In the Box

your-repo/
├── .ai/                    ← git submodule (shared, forkable)
│   ├── AGENTS.md            ← master entry point for all AI agents
│   ├── project.yaml         ← per-project manifest (local copy)
│   ├── project.yaml.example ← config template
│   ├── skills/              ← 17 slash commands (source of truth)
│   ├── rules/
│   │   ├── global/          ← universal rules (12 files)
│   │   ├── stacks/          ← per-stack rules (nodejs, nextjs, …)
│   │   └── project/         ← (deprecated, use .ai-local/rules/)
│   ├── personas/            ← role definitions (architect, implementer, …)
│   ├── overrides/           ← (deprecated, use .ai-local/overrides/)
│   ├── templates/           ← doc templates (plan, spec, brief, …)
│   └── .scripts/            ← install & update scripts
│
├── CLAUDE.md ──────────────→ symlink to .ai/AGENTS.md
├── GEMINI.md ──────────────→ symlink to .ai/AGENTS.md
├── .github/copilot-instructions.md → symlink to .ai/AGENTS.md
├── .claude/skills/*/SKILL.md ────→ per-file symlinks to .ai/skills/
└── .gemini/commands/*.toml ──────→ per-file symlinks to .ai/.gemini/commands/

The submodule holds everything reusable. Project-specific config (project.yaml and .ai-local/rules/) lives inside the consumer repo. Symlinks bridge them to each agent tool's expected paths.

Anatomy: Why Each Part Exists

📘 AGENTS.md

Why: Single entry point all three AI tools resolve to (via symlinks). Sets the routing contract: "read project.yaml first, load rules by precedence, adopt your persona."

⚙️ project.yaml

Why: Per-project manifest declaring name, stack, which rules to load, which personas to enable, and doc paths. Created from the example template on install.

🛠️ Skills

Why: Reusable slash commands (spec, plan, implement, review, …) that form a complete dev workflow. Written once in SKILL.md format, symlinked to Claude, Copilot, and Gemini.

📏 Rules

Why: Coding standards the agent must follow. Global rules (12) are universal. Stack rules teach the language. Project rules override specifically for this repo.

🎭 Personas

Why: Role definitions (architect, implementer, reviewer, …) that shape how the agent works — tone, focus, escalation triggers. Stack-agnostic; rules teach the stack.

📄 Templates

Why: Standardised document shapes (plan, spec, brief) with frontmatter schemas. Skills reference templates when creating docs — guaranteeing consistent structure and cross-linking.

🔗 Symlinks

Why: Git stores them as mode 120000 — they survive clone. Per-file symlinks (not directory) because Windows git checkout creates file symlinks only. Zero maintenance after install.

📚 Terminology

Why: Shared vocabulary and domain definitions. Ensures agents use the same business terms and concepts across all artifacts, reducing ambiguity between product and engineering.

Rules: Layered & Stack-Specific

Rules load in precedence order (core -> contextual -> target -> local). A local rule with the same filename replaces a global one.

Global Rules (12 files)

  • 00 — Intent Routing
  • 01 — Principles
  • 02 — Agent Conduct
  • 03 — Documentation
  • 04 — Doc Lifecycle
  • 05 — Version Control
  • 06 — Testing
  • 07 — Dependencies
  • 08 — Secrets & Data
  • 09 — Observability & Errors
  • 10 — Design System
  • 11 — Validation Discipline

Stack Rules (8 files each)

  • 01 — Constraints

Available stacks: dotnet, nextjs, nodejs, react-native, rust 

  .ai-local/project.yaml:
    rules:
      core:
        - .ai/rules/global/*           ← always loaded
        - .ai/rules/stacks/nextjs/*    ← your stack
      contextual:
        - .ai/rules/global/*.md        ← task-aligned
        - .ai-local/rules/*.md         ← task-aligned

Getting Started

Install (once)

  1. Add the submodule: 
    git submodule add <url> .ai
  2. Run the install script: 
    # PowerShell (Windows)
.ai/.scripts/install-symlinks.ps1

# Shell (Linux / macOS)
sh .ai/.scripts/install-symlinks.sh
  3. Interactive Setup: Follow the prompts to set your project name and select your tech stack.
  4. Commit .ai-local/project.yaml and symlinks

Update (periodic)

# PowerShell
.ai/.scripts/update-submodule.ps1

# Shell
sh .ai/.scripts/update-submodule.sh

The update script:

  • Pulls the latest submodule (--remote)
  • Prunes dead symlinks (removed skills/commands)
  • Creates new symlinks (added skills/commands)
  • Stages everything for commit

Cloning a repo that uses dot-ai

git clone -c core.symlinks=true <repo-url>
cd <repo>
git submodule update --init

core.symlinks=true is needed on Windows so git creates real symlinks instead of text files.

Fork & Make It Yours

dot-ai is partially company-specific by design. Fork the repo, then:

Add your stack

Create rules/stacks/your-stack/ with 8 rule files following the existing pattern. Your conventions, your tools.

Tune personas

Edit personas/*.md to match your team's roles, tone, and escalation policies.

Add skills

Drop a SKILL.md in skills/your-skill/. The install script auto-discovers and symlinks it to all agents.

Override per-project

Put project-specific rules in .ai-local/rules/ and persona tweaks in .ai-local/overrides/. They stay in your repo, not the submodule.
