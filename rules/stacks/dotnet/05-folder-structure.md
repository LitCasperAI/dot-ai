# .NET Folder Structure

Organised by domain, not by technical type. Two reference
layouts are provided: one for backend services (Web API /
worker), one for NuGet libraries.

---

## Backend service layout

```text
src/
├── <ServiceName>.Api/           # Hosting & HTTP layer
│   ├── Program.cs               # Composition root: DI, middleware, listen
│   ├── Endpoints/               # Minimal API route groups (or Controllers/)
│   │   └── Users/
│   │       ├── UserEndpoints.cs # Route definitions (thin)
│   │       └── UserModels.cs    # Request/response DTOs for this group
│   ├── Middleware/               # Cross-cutting middleware (auth, errors, correlation)
│   ├── Filters/                  # Endpoint filters (validation, logging)
│   └── appsettings.json
├── <ServiceName>.Domain/        # Domain model — no dependencies on infrastructure
│   ├── Users/
│   │   ├── User.cs              # Aggregate / entity
│   │   ├── IUserRepository.cs   # Repository interface (port)
│   │   └── UserErrors.cs        # Domain-specific typed errors
│   └── Common/
│       └── DomainException.cs   # Base domain exception / result types
├── <ServiceName>.Application/   # Use cases / services
│   ├── Users/
│   │   ├── CreateUserCommand.cs # Command / handler (MediatR or plain class)
│   │   ├── GetUserQuery.cs
│   │   └── UserService.cs       # Orchestration if not using CQRS
│   └── Common/
│       ├── Interfaces/           # Ports for infrastructure
│       └── Behaviours/           # MediatR pipeline behaviours (validation, logging)
├── <ServiceName>.Infrastructure/ # Implementations of ports
│   ├── Persistence/
│   │   ├── AppDbContext.cs       # EF Core DbContext
│   │   ├── Migrations/           # EF migrations (forward-only)
│   │   ├── Configurations/       # IEntityTypeConfiguration<T> per entity
│   │   └── Repositories/
│   │       └── UserRepository.cs # IUserRepository implementation
│   ├── ExternalApis/             # Typed HTTP clients (via IHttpClientFactory)
│   └── Messaging/                # Queue producers / consumers
└── <ServiceName>.Tests/          # All tests for the service
    ├── Unit/
    ├── Integration/
    └── TestInfrastructure/       # WebApplicationFactory, Testcontainers, seed helpers

load/                             # k6 / NBomber load test scripts
```

## Library layout

```text
src/
├── <PackageName>/               # Main library project
│   ├── <PackageName>.csproj
│   ├── PublicApi/                # Public-facing types
│   ├── Internal/                 # `internal` implementation details
│   └── GlobalUsings.cs
├── <PackageName>.Specs/         # Functional / unit tests (xUnit + FluentAssertions)
├── <PackageName>.ApiVerificationTests/  # Verify-based API snapshot tests
│   └── ApprovedApi/             # .txt snapshots per target framework
build/                            # Nuke build scripts
```

## Key boundaries

- **`Domain` has zero project references.** It depends on
  nothing but the BCL. This is the innermost ring.
- **`Application` references `Domain` only.** It defines ports
  (interfaces) for infrastructure.
- **`Infrastructure` references `Application` and `Domain`.**
  It implements the ports.
- **`Api` references everything** and wires them up in
  `Program.cs`.
- **Tests reference `Api`** (for `WebApplicationFactory`) and
  transitively reach everything.

## Feature encapsulation

- **Feature folders group by domain concept**, not by technical
  type. `Users/` contains the endpoint, service, repository
  interface, entity, and errors for users — all in one place.
- **Cross-feature calls go through service interfaces**, never
  by reaching into another feature's internals.
- **Shared code** lives in `Common/` or a `SharedKernel`
  project, never in a feature folder.

## Migrations

- **Migrations live in `Infrastructure/Persistence/Migrations/`**
  and are generated by EF Core tooling. They are
  forward-only; see `07-build-and-release.md`.
- **A migration PR is its own PR** unless the migration is
  small, additive, and inseparable from the feature. Complex
  migrations are never bundled with feature work.

## Tests

- Tests live in a dedicated test project, per `02-testing.md`.
  Not colocated with production code.
- Shared test utilities (Testcontainer helpers, request
  builders, seed data) live in `TestInfrastructure/` and are
  never referenced from production projects.

## What does not live where

- **No business logic in `Api/`.** Endpoints call services;
  services own the rules.
- **No direct DbContext access from endpoints.** Endpoints call
  services, services call repositories.
- **No EF Core references in `Domain/`.** The domain model has
  no awareness of persistence.
- **No cross-feature internal imports.** If `Orders` needs
  something from `Users`, call through an interface or
  graduate the shared code.
